# [US-030] Light mode, following the system preference, with a "Thème" selector

> **Epic:** v1 finalisation
> **Status:** DONE (automated gates passed, manual browser checks pending; see `docs/reviews/REVIEW-US-030.md`)

## 1. User Story Statement

**As an** eco-design auditor working in the DevTools panel,
**I want** the extension to follow my light or dark appearance preference, and to be able to force light or dark,
**So that** the panel stays readable and comfortable in my working environment, for example a light theme in a bright room or when sharing my screen.

## 2. Context & Detailed Description

### Today

The panel is **dark only**:
- the colours are fixed in `tailwind.config.js` (`background #282828`, `surface #3C3C3C`…);
- `text-white` and `outline-white` are hard-coded in many places;
- icons have fixed fill colours;
- Chart.js, the US-020 syntax palette (tested at 4.5:1 on the dark background only) and the EcoIndex grade badges have their own colours.

### Modes

These are owner decisions.

| Mode (label) | Effect |
|---|---|
| `Système` (default) | follows `prefers-color-scheme`, which is the OS or browser appearance setting. It **updates live** when that setting changes, without reloading the panel. |
| `Clair` | light theme, whatever the system says |
| `Sombre` | dark theme, whatever the system says. It is the current look, unchanged. |

### Selector

This is an owner decision.

- A **select** in the toolbar, at the top right, **immediately to the left of "A propos"**.
- It is styled like the existing analysis selector.
- Its visible label is **`Thème`**, a `<label>` next to it. Its options are `Système`, `Clair` and `Sombre`, in that order.
- Changing it applies the theme **immediately**, without a reload, on every screen: the home page and launch form, the recording, saved analyses, "À propos", and open dialogs.

### Persistence

- The choice is **remembered** in the panel's `localStorage`, under its own key, separate from the analyses store.
- It applies the next time the panel opens.
- **Fallbacks:** storage unavailable, or an unknown value, means `Système`. A storage failure never shows an error. The choice then lasts only for the session.
- **Several open panels** (two DevTools windows): changing the theme in one updates the others live (PO default).
- The theme is applied **before the first paint**, so a light-mode user never sees a dark flash on opening.

### What must adapt

Every element of the panel app must have a light variant. Dark keeps its current look.

- surfaces, backgrounds, borders, table stripes and text;
- buttons, including their hover, disabled and danger variants;
- form fields, the focus outline (today `outline-white`, which would be invisible on light), and the native controls and scrollbars (the CSS `color-scheme`);
- icons, which follow the text colour;
- the loader, tooltips and the dialog backdrop;
- best-practice panels:
  - compliance badges;
  - the "Non évaluée" chip;
  - the reference label (US-028);
  - the indicator (US-029);
- EcoIndex grade badges. The grade colours from `ecoindex_reference` are kept, and the grade letter must stay readable on them in both themes;
- charts (Chart.js): axes, grid lines, labels, tooltips and legends. They follow a theme change without a reload;
- dialogs (`AppDialogProvider`):
  - the comparison dialog;
  - the image, media, iframe and font previews;
  - the **text preview**: its syntax palette needs a **light palette**, tested at 4.5:1 or more on the light background, like the dark one (ARCH-DECISION-025);
- image previews: images keep their own colours; only the frame and its information adapt.

### Light palette

- The team lead derives it from the existing tokens.
- The brand blue (`primary`) and `btn` are kept, with darker or lighter steps where contrast requires.
- **WCAG 2.1 AA:**
  - at least **4.5:1** for text;
  - at least **3:1** for UI component boundaries and focus indicators.
- These ratios are checked by tests on the colour tokens of both themes.

## 3. Tech Stack Hints & Scope Constraints

- **In scope:**
  - the theme tokens for both themes;
  - the pure theme logic (mode, resolution against the system, persistence, fallback);
  - the toolbar select;
  - adapting every component listed above;
  - the contrast tests;
  - README and CHANGELOG.
- **Out of scope:**
  - following the DevTools theme (`devtools.panels.themeName`). The owner chose the OS or browser preference;
  - high-contrast or `forced-colors` mode beyond not breaking;
  - user-defined colours;
  - theming the inspected page;
  - the extension icon.
- **Hints for the team lead:**
  - Prefer CSS custom properties for the tokens, switched by a class or attribute on `<html>`, with Tailwind colours referring to them. This avoids doubling every class with `dark:`. The choice is yours; record it in an ARCH-DECISION.
  - **Before first paint:**
    - The extension CSP forbids inline scripts. Do not relax it; `scripts/manifest.test.mjs` must keep passing.
    - Apply the theme from an external module that runs first, or from CSS: `prefers-color-scheme` handles `Système` without JavaScript, and only forced modes need the stored value.
  - Chart.js reads colours when a chart is created or updated. Charts must re-render on a theme change.
  - The theme logic is pure and tested, with `matchMedia` and storage injected. The `.tsx` files only wire it.
  - The domain is untouched. This is UI and infra only.
- **Persistence:** one `localStorage` key, holding `"system"`, `"light"` or `"dark"`. There is no SQLite.

## 4. Acceptance Criteria (Gherkin Scenarios)

### Scenario 1: Happy path, the system is light
Given no theme was ever chosen and the OS appearance is light
When the panel opens
Then the light theme is shown from the first paint
And the "Thème" select shows "Système"

### Scenario 2: The system changes while the panel is open
Given the mode is "Système" and the OS appearance is light
When the OS switches to dark
Then the panel switches to the dark theme without reload, charts included

### Scenario 3: Force light
Given the OS appearance is dark
When the auditor selects "Clair"
Then the light theme applies immediately on the current screen
And when the OS appearance changes, the panel stays light

### Scenario 4: Force dark
Given the OS appearance is light
When the auditor selects "Sombre"
Then the dark theme applies and looks exactly as before this story

### Scenario 5: Remembered
Given the auditor selected "Clair" and closed DevTools
When they open the panel again
Then the light theme is shown from the first paint, and the select shows "Clair"

### Scenario 6: Back to system
Given the mode is "Clair" and the OS appearance is dark
When the auditor selects "Système"
Then the dark theme applies

### Scenario 7: Storage unavailable or corrupt
Given `localStorage` throws, or the stored value is "blue"
When the panel opens
Then the mode is "Système", with no error message
And selecting a mode still applies it for the session

### Scenario 8: Two panels
Given two DevTools panels of the extension are open
When the theme is changed to "Sombre" in one
Then the other switches to dark too

### Scenario 9: Theme change with an open dialog and a text preview
Given a text preview of a JS file is open
When the theme changes, for example through the OS in "Système" mode
Then the dialog and the syntax colours switch to the new theme's palette

### Scenario 10: Contrast
Given the colour tokens of each theme
Then every text-on-surface pair used by the app has a contrast of 4.5:1 or more
And every boundary and focus-indicator pair has 3:1 or more
And every syntax token colour has 4.5:1 or more on its theme's preview background
And the EcoIndex grade letters keep 4.5:1 or more on their badge colour in both themes, or the badge gets a readable text colour

### Scenario 11: Position and labelling
Then the toolbar shows "Thème" and its select immediately to the left of "A propos"
And the select is reachable with Tab, labelled "Thème", and has the options "Système", "Clair" and "Sombre" in that order

### Scenario 12: The CSP is unchanged
Then `scripts/manifest.test.mjs` passes without modification of the extension pages' CSP

## 5. Non-Functional Requirements (NFRs) & Constraints

- **Performance:**
  - A theme switch completes within one frame, about 16 ms, for the DOM.
  - Charts re-render within 100 ms.
  - There is no visible flash on opening.
- **Accessibility:**
  - WCAG 2.1 AA contrast in both themes (scenario 10).
  - The focus is visible in both themes.
  - The select is a native `<select>` with a `<label>`.
- **Compatibility:** Chrome 103 or later and Firefox 109 or later, in the DevTools panel; also `npm run dev`.
