# [US-002] Use optimised image formats (AVIF for photos, lossless WebP for graphics)

> **Epic:** Image optimisation (US-001 → US-002 → US-003)
> **Depends on:** US-001, which provides the estimation pipeline (image bytes, Web Worker, WebAssembly codecs, cache, caps)
> **Status:** READY FOR TDD

## 1. User Story Statement

**As an** eco-design auditor,
**I want** each page to report the JPEG and PNG images that would be lighter in a modern format, with the estimated kilobytes saved per image,
**So that** I can recommend a concrete format change backed by measured gains.

## 2. Context & Detailed Description

This adds a new best practice: **"Utiliser des formats d'image optimisés"**, id `UseOptimizedImageFormats`, category `images`.

### Conversion policy

These are product decisions.

| Source format (detected) | Recommended format | Encoding settings |
|---|---|---|
| JPEG (photos) | **AVIF** | quality **65** (`sharp` `avif({ quality: 65 })` equivalent) |
| PNG (graphics, transparency) | **WebP** | **lossless** (`webp({ lossless: true })` equivalent) |
| WebP, AVIF | — | already compliant, not listed |
| GIF, APNG, animated WebP, BMP, TIFF, ICO | — | out of scope: not estimated, not counted |

### Rules

1. **Format detection.** Use the **response MIME type** of the image request. If it is missing or generic (`application/octet-stream`), fall back to the file signature (magic bytes). **Never** use the file extension: `photo.jpg` served as `image/webp` is WebP.
2. **Gain estimation.** The original file is re-encoded **at its natural size** in the recommended format, with the US-001 pipeline. `formatGain = originalBytes − convertedBytes`, clamped at 0, where `originalBytes` is the transferred size.
3. **No penalty when conversion doesn't help.** When the converted file is not smaller, the image is not an offender.
4. **Noise threshold and grade** are the same as US-001:
   - images whose gain is under 10 kB are ignored;
   - the share is `sum(formatGain) / evaluated image bytes`;
   - **A** below 10%, **B** from 10% to 30%, **C** above 30%.
5. **Image set.** All images downloaded by the page whose detected format is in the table, *including* those not shown, are evaluated, as long as their bytes are available. Displayed size is irrelevant here; an image shown at 0×0 is still downloaded.
   - This differs from US-001's set on purpose. The same image may be counted by both rules; US-003 removes the double counting.
6. **UI detail.** Offenders are sorted by gain, in descending order, at most 20 lines:
   `photo.jpg : JPEG 240 ko → AVIF ≈ 96 ko, gain estimé 144 ko`
7. **Asynchronous behaviour, caching, caps, "non évaluée" reasons and stop behaviour** are the same as US-001, scenarios 8 to 12.

## 3. Tech Stack Hints & Scope Constraints

- **In scope:**
  - the new rule;
  - format detection;
  - AVIF and lossless WebP encoders added to the US-001 pipeline;
  - registration in `RULES`;
  - UI detail.
- **Out of scope:**
  - generating or downloading converted files;
  - `<picture>` / `type=` fallback advice;
  - JPEG XL;
  - quality tuning per image (fixed settings above);
  - totals and CSV (US-003).
- **Hint:** the AVIF encoder is the slowest codec. The US-001 caps apply, and the team lead should measure the encode time on a 2-megapixel photo and report it.
- **State:** per image `pending | estimated | skipped(reason) | failed(reason)`, shared with US-001's cache. Cache entries are keyed by URL and by transformation, so a "resize" result and an "AVIF" result for the same image are distinct entries.
- **Persistence:** stored with the analysis, as in US-001. Older saved analyses simply don't have this rule.

## 4. Acceptance Criteria (Gherkin Scenarios)

### Scenario 1: Happy path: JPEG photo converted to AVIF
Given the page downloaded "photo.jpg" served as "image/jpeg" with 240 kB transferred
And encoding it in AVIF at quality 65 at its natural size is estimated at 96 kB
When the best practices of the page are evaluated
Then "photo.jpg" is listed with "JPEG 240 ko → AVIF ≈ 96 ko" and an estimated gain of 144 kB

### Scenario 2: Happy path: PNG converted to lossless WebP
Given the page downloaded "logo.png" served as "image/png" with 50 kB transferred
And encoding it in lossless WebP is estimated at 35 kB
When the best practices of the page are evaluated
Then "logo.png" is listed with "PNG 50 ko → WebP sans perte ≈ 35 ko" and an estimated gain of 15 kB

### Scenario 3: Already optimised formats
Given the page only downloaded images served as "image/webp" and "image/avif"
When the best practices of the page are evaluated
Then the rule is graded "A"
And no image is listed

### Scenario 4: Conversion would not reduce weight
Given "icon.png" is 4 kB and its lossless WebP version is estimated at 5 kB
When the best practices of the page are evaluated
Then "icon.png" is not listed
And its gain counts as 0 kB

### Scenario 5: Format is detected from the response, not the extension
Given "photo.jpg" is served with the content type "image/webp"
When the best practices of the page are evaluated
Then "photo.jpg" is treated as WebP and not listed

### Scenario 6: Missing content type falls back to file signature
Given "img/42" is served as "application/octet-stream" and its bytes start with the PNG signature
When the best practices of the page are evaluated
Then "img/42" is treated as PNG and estimated in lossless WebP

### Scenario 7: Out-of-scope formats
Given the page downloaded an animated GIF, an animated PNG and an ICO file
When the best practices of the page are evaluated
Then none of them are estimated, listed or counted in the evaluated image weight

### Scenario 8: Grading by share of image weight
Given the evaluated images of a page weigh 500 kB in total
When the sum of the format gains is <gain>
Then the rule grade is <grade>

Examples:
| gain   | grade |
| 40 kB  | A     |
| 120 kB | B     |
| 200 kB | C     |

### Scenario 9: Encoder failure on one image
Given the AVIF encoding of "broken.jpg" throws an error
When its estimation ends
Then "broken.jpg" is marked "non évaluée (échec de l'encodage)"
And the other images are graded normally

## 5. Non-Functional Requirements (NFRs) & Constraints

- **Responsiveness and sobriety:** the same as US-001: Web Worker, one estimate per URL and transformation, a queue of 1, and the 25 MP / 10 MB caps. The AVIF and WebP codecs are lazy-loaded.
- **Fidelity:** the estimated size must come from real encoding with the stated settings. A ratio-based estimate is not acceptable.
- **Accessibility:** the same as US-001.
- **Cross-browser:** identical results on Chrome and Firefox for the same image bytes.
