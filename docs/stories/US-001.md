# [US-001] Don't resize images in the browser: density-aware detection with estimated gain

> **Epic:** Image optimisation (US-001 → US-002 → US-003)
> **Replaces:** the current `DontResizeImagesInBrowser` rule (`src/app/domain/best-practices/rules/dont-resize-images.rule.ts`)
> **Status:** READY FOR TDD

## 1. User Story Statement

**As an** eco-design auditor recording a user journey with EcoInsights,
**I want** each page to report the images downloaded at a higher definition than the screen can display, together with the kilobytes saved by serving them at the right size,
**So that** I can prioritise image fixes by actual weight saved instead of by a raw list of resized images.

## 2. Context & Detailed Description

Today the rule compares an image's natural size with its CSS display size in CSS pixels. On high-density displays (Retina Macs, most phones) one CSS pixel covers `devicePixelRatio` physical pixels, typically 2. A 600×400 image shown in a 300×200 CSS box is therefore *correctly* sized on a 2x screen, yet flagged today. The rule also says nothing about how much weight is at stake.

### Target behaviour

1. **Density.** The density used is the **current screen's** `window.devicePixelRatio`, read in the inspected page at collection time. This was a product decision. The value used is stored with the page and displayed, for example "Densité d'écran : 2x".
2. **Required size of an image** = CSS display box (`getBoundingClientRect` width × height) × density, rounded up.
3. **Oversized image.** The scale factor is `f = max(requiredWidth / naturalWidth, requiredHeight / naturalHeight)`, so the image keeps its aspect ratio and still covers the box. The image is oversized when `f < 1`. The target size is `round(natural × f)`.
4. **Gain estimate.** For each oversized image, the original file is **resized to the target size and re-encoded in its own format**, by real encoding with WebAssembly codecs, the equivalent of `sharp` in the browser. `resizeGain = originalBytes − resizedBytes`, clamped at 0.
   - `originalBytes` is the image's **transferred** size from the page's network data.
   - **Re-encoding settings (PO default):** the same quality as a typical `sharp` default for that format. JPEG uses quality 80 with mozjpeg, PNG uses compression 9, and WebP and AVIF keep their source quality range. The resize filter is Lanczos3, sharp's default.
5. **Noise threshold.** An image whose `resizeGain` is under **10 kB** is not reported as an offender, and its gain is not counted.
6. **Grade** (decided by the product owner). The share is `sum(resizeGain of offenders) / sum(originalBytes of the evaluated images of the page)`:
   - **A** below 10%;
   - **B** from 10% to 30%;
   - **C** above 30%.
7. **Estimation pipeline.** This story builds the pipeline that US-002 and US-003 reuse:
   - obtain the original image bytes;
   - decode, resize and encode in a **Web Worker** in the DevTools panel, so the UI never freezes;
   - cache results by image URL for the whole analysis;
   - apply the caps listed in §5.
8. **Asynchronous results.** Estimation takes time, so the rule appears first with the status **"Estimation en cours… (n/m images)"**. It is updated live as images are estimated.
9. **UI.** The rule's detail lists offenders sorted by gain, in descending order:
   `photo.jpg : 1200×800 pour un affichage en 300×200 (×2 → 600×400), gain estimé 180 ko`.
   Show at most 20 lines, then "… et N autres images".

### Rule identity

Keep the id `DontResizeImagesInBrowser` and the name "Ne pas redimensionner les images dans le navigateur". Saved analyses produced before this story are displayed as they were saved, with no gain shown.

## 3. Tech Stack Hints & Scope Constraints

- **In scope:**
  - `<img>` elements, including those inside `<picture>` and with `srcset`. Use `currentSrc`, the resource actually chosen by the browser.
  - The DPR-aware detection.
  - The resize gain estimation and the shared estimation pipeline.
  - Grading and the UI detail.
- **Out of scope:**
  - CSS `background-image`, `<svg>`, `<canvas>` and `<video>` posters.
  - Format recommendations (US-002) and page or analysis totals and CSV (US-003).
  - Recommending `srcset` markup.
- **Architecture warnings for the team lead (not decisions):**
  - `BestPracticeRule.evaluate` is pure and **synchronous** (ARCH-DECISION-004). Asynchronous, CPU-heavy estimation does not fit it as is. Where estimation lives needs a decision, and probably an amendment to ARCH-DECISION-004: a new port, a rule "estimator" phase, or a domain service.
  - **Image bytes** can come from DevTools (`request.getContent()`), but only for requests seen after recording starts. Other images may need a re-fetch from the background page agent. Any re-fetch **must not** be counted in the page's measured requests or EcoIndex.
  - MV3 extension pages need `'wasm-unsafe-eval'` in `content_security_policy.extension_pages` to run WebAssembly, on both Chrome and Firefox. The manifest generation (ARCH-DECISION-005) must add it.
  - Candidate codecs: `@jsquash/*`, the Squoosh codecs compiled to WebAssembly, including resize. The team lead chooses and records the choice in an ARCH-DECISION.
- **State per image:** `pending` → `estimated` | `skipped(reason)` | `failed(reason)`.
- **State per rule:** "Estimation en cours" while any image is `pending`, then graded.
- **Persistence:** results are stored with the `Analysis` in the existing local store (`localStorage`, see `store.tsx`), not SQLite. Saved analyses must keep loading (`store-codec.ts` migration).

## 4. Acceptance Criteria (Gherkin Scenarios)

### Scenario 1: Happy path: oversized image on a 2x screen
Given the inspected screen has a devicePixelRatio of 2
And the page shows "photo.jpg" with a natural size of 1200×800 in a CSS box of 300×200
And "photo.jpg" was transferred with 240 kB
And resizing "photo.jpg" to 600×400 in JPEG is estimated at 60 kB
When the best practices of the page are evaluated
Then "photo.jpg" is listed as an offender with a required size of 600×400 and an estimated gain of 180 kB
And the page displays "Densité d'écran : 2x"

### Scenario 2: High-density correctness: not flagged on a 2x screen
Given the inspected screen has a devicePixelRatio of 2
And the page shows "hero.jpg" with a natural size of 600×400 in a CSS box of 300×200
When the best practices of the page are evaluated
Then "hero.jpg" is not listed as an offender

### Scenario 3: Same image flagged on a 1x screen
Given the inspected screen has a devicePixelRatio of 1
And the page shows "hero.jpg" with a natural size of 600×400 in a CSS box of 300×200
And resizing it to 300×200 is estimated to save 40 kB
When the best practices of the page are evaluated
Then "hero.jpg" is listed as an offender with an estimated gain of 40 kB

### Scenario 4: Grading by share of image weight
Given the evaluated images of a page weigh 1000 kB in total
When the sum of the offenders' resize gains is <gain>
Then the rule grade is <grade>

Examples:
| gain   | grade |
| 50 kB  | A     |
| 100 kB | B     |
| 300 kB | B     |
| 301 kB | C     |

### Scenario 5: Noise threshold
Given an oversized image whose estimated resize gain is 8 kB
When the best practices of the page are evaluated
Then the image is not listed as an offender
And its gain is not counted in the rule's share

### Scenario 6: Upscaled or exact-size image
Given the page shows an image whose natural size is smaller than or equal to its required size
When the best practices of the page are evaluated
Then the image is not listed as an offender

### Scenario 7: Images excluded from the analysis
Given the page contains an SVG image, a "data:" image, an animated GIF, a lazy image not yet loaded (naturalWidth 0) and an image displayed at 0×0
When the best practices of the page are evaluated
Then none of these images are estimated or listed
And they are not counted in the page's evaluated image weight

### Scenario 8: Asynchronous estimation in progress
Given a page with 5 oversized images and 2 of them already estimated
When the auditor opens the best-practices panel
Then the rule shows "Estimation en cours… (2/5 images)" and no grade yet
And the rule is updated without user action when the remaining images are estimated

### Scenario 9: Image too large to estimate
Given the page shows an oversized image of 30 megapixels
When the best practices of the page are evaluated
Then that image is marked "non évaluée (image trop volumineuse)" and excluded from the share
And the rule is graded on the other images

### Scenario 10: Image bytes unavailable or encoding failure
Given the original bytes of an oversized image cannot be obtained, or its encoding throws
When the estimation of that image ends
Then the image is marked "non évaluée" with the reason
And the other images are still estimated and graded
And if no image of the page could be evaluated, the rule shows "Non évaluée"

### Scenario 11: Same image on several pages
Given "logo.png" (1000×1000, shown at 100×100) appears on 3 recorded pages
When the best practices of the 3 pages are evaluated
Then "logo.png" is decoded and encoded only once during the analysis
And each page lists it with the same estimated gain

### Scenario 12: Stopping the analysis while estimations are pending
Given 3 images are still "pending"
When the auditor clicks "Stopper l'analyse"
Then the analysis is saved immediately
And the 3 images are saved as "non évaluée (analyse arrêtée)"
And the grade is computed on the images already estimated

### Scenario 13: Browser zoom changes the density
Given the auditor's screen is 1x and the browser zoom is 150%
When the best practices are collected
Then the density used is 1.5 and "Densité d'écran : 1.5x" is displayed

## 5. Non-Functional Requirements (NFRs) & Constraints

- **Responsiveness:** all decoding and encoding runs off the UI thread, in a Web Worker. The panel stays interactive, with no task over 50 ms on the main thread caused by estimation.
- **Sobriety caps (PO defaults):**
  - one encode per image URL per analysis;
  - at most 1 image estimated at a time, through a FIFO queue;
  - images over **25 megapixels** or **10 MB** are skipped as "trop volumineuse".
- **Bundle:** WebAssembly codecs are loaded lazily, only when an analysis with best practices starts. They are not loaded by `npm run dev` with the mock unless needed. The team lead reports the size added to `dist/<target>`.
- **No measurement bias:** fetching image bytes must never add requests to the page's measured requests, DOM profile or EcoIndex.
- **Accessibility:**
  - the "Estimation en cours" status is announced (`role="status"`);
  - offender lists stay inside the existing keyboard-accessible expand/collapse buttons.
- **Cross-browser:** identical behaviour on Chrome and Firefox (ARCH-DECISION-001).
