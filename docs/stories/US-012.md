# [US-012] Prefer HTTP/2 over HTTP/1

> **Epic:** BP2 (see [EPIC-BP2-conventions.md](EPIC-BP2-conventions.md))
> **Rule:** `PreferHttp2`, "Privilégier HTTP/2 à HTTP/1", category `network`
> **Status:** DONE (automated gates passed, manual browser checks pending; see `docs/reviews/REVIEW-US-006-014.md`)

## 1. User Story Statement

**As an** eco-design auditor,
**I want** each page to report the share of its requests still served over HTTP/1.x,
**So that** the site owner can enable HTTP/2 or HTTP/3, which multiplexes requests over fewer connections.

## 2. Context & Detailed Description

### Data: HTTP version per request

This part touches infrastructure.

- The request model (`NetworkRequest`) gains an optional **`httpVersion`** field, normalised to `"1.0" | "1.1" | "2" | "3"`. It is `undefined` when the version is unknown.
- It comes from the recorded response's protocol (HAR `response.httpVersion`). The values differ by browser:

| Raw value | Normalised |
|---|---|
| `HTTP/1.0`, `http/1.0` | `1.0` |
| `HTTP/1.1`, `http/1.1` | `1.1` |
| `HTTP/2`, `HTTP/2.0`, `http/2.0`, `h2`, `h2c` | `2` |
| `HTTP/3`, `h3`, `h3-29` and other `h3-*` drafts | `3` |
| empty, `unknown`, anything else | `undefined` |

- The field is optional, so analyses saved before this story still load.

### Requests counted

- Requests with a **known** version.
- Responses **served from the browser cache** are excluded: no network transfer, `transferSize` of 0 with a 2xx status. They often report no version or a misleading one. `304` responses do count, as they travel over the network.

### Grade

This was a product decision for the 10 % boundary, which the request leaves undefined.

- `share` = HTTP/1.x requests ÷ counted requests.
- **A:** `share` = 0: "Toutes les requêtes utilisent HTTP/2 ou HTTP/3".
- **B:** 0 < `share` < 10 %.
- **C:** `share` ≥ 10 %.
- **Non évaluée:** no request with a known version. Detail: "Version HTTP inconnue pour toutes les requêtes".

### Detail and lines

- Detail: "<p> % des requêtes en HTTP/1 (<k> sur <n>)".
- Lines:
  - one per domain serving HTTP/1.x requests: `<domain> : <k> requête(s) en HTTP/1.1`;
  - the version shown is the most frequent one for that domain;
  - sorted by count, largest first.

## 3. Tech Stack Hints & Scope Constraints

- **In scope:**
  - `httpVersion` in the HAR normaliser (`har.ts`), with tests on Chrome-like and Firefox-like entries;
  - the field in `NetworkRequest` and in the store codec, persisted as is;
  - the rule.
- **Out of scope:**
  - detecting HTTP/3 availability (`alt-svc`);
  - connection reuse;
  - TLS version.
- **Edge:** a local development server (`localhost`, Vite or webpack-dev-server) is always HTTP/1.1, so auditing it gives C. This is expected and documented in the rule detail. No special case.
- **State:** synchronous.
- **Persistence:** stored with the page. `httpVersion` is stored with each request.

## 4. Acceptance Criteria (Gherkin Scenarios)

### Scenario 1: Happy path: everything over HTTP/2 or HTTP/3
Given the page made 40 network requests, 30 in "h2" and 10 in "h3"
When the best practices are evaluated
Then the rule is graded "A" with the detail "Toutes les requêtes utilisent HTTP/2 ou HTTP/3"

### Scenario 2: Under 10 % HTTP/1 gives B
Given 50 counted requests, 3 of them "http/1.1"
When the best practices are evaluated
Then the rule is graded "B" with the detail "6 % des requêtes en HTTP/1 (3 sur 50)"

### Scenario 3: Boundary: exactly 10 % gives C
Given 50 counted requests, 5 of them HTTP/1.1
When the best practices are evaluated
Then the rule is graded "C"

### Scenario 4: Lines grouped by domain
Given 4 HTTP/1.1 requests to "legacy.example.org" and 2 to "ads.example.net"
When the best practices are evaluated
Then the lines are "legacy.example.org : 4 requêtes en HTTP/1.1" then "ads.example.net : 2 requêtes en HTTP/1.1"

### Scenario 5: Version normalisation across browsers
Given HAR entries with versions "HTTP/2", "http/2.0", "h2", "h3-29", "HTTP/1.1", "" and "unknown"
When they are normalised
Then the versions are "2", "2", "2", "3", "1.1", undefined and undefined

### Scenario 6: Cached responses are excluded
Given 10 requests served from cache (2xx, transfer size 0) without a version, and 5 network requests in "h2"
When the best practices are evaluated
Then the share is computed on the 5 network requests and the rule is graded "A"

### Scenario 7: No known version
Given every request of the page has an unknown version
When the best practices are evaluated
Then the rule shows "Non évaluée" with the detail "Version HTTP inconnue pour toutes les requêtes"

### Scenario 8: Legacy analysis
Given an analysis saved before this story, whose requests have no `httpVersion`
When it is loaded
Then it loads without error and its stored best practices are displayed unchanged

## 5. Non-Functional Requirements (NFRs) & Constraints

- **Performance:** linear; 2 000 requests in under 10 ms.
- **Cross-browser:** the normalisation table covers both Chrome and Firefox HAR values.
