# [US-025] Limit the number of HTTP requests

> **Epic:** BP3 (see [EPIC-BP3-conventions.md](EPIC-BP3-conventions.md))
> **Rule:** `LimitRequests`, "Limiter le nombre de requêtes HTTP", category `network`
> **Status:** DONE (automated gates passed, manual browser checks pending; see `docs/reviews/REVIEW-US-024-027.md`)

## 1. User Story Statement

**As an** eco-design auditor,
**I want** each page to be graded on its number of HTTP requests,
**So that** the site owner reduces the requests, each of which costs server, network and device resources.

## 2. Context & Detailed Description

### Requests counted

- **Every request recorded for the page,** which is exactly the number in the "Requêtes" column of the page table and the one EcoIndex uses. The two counts must never disagree.
- Third-party, failed (4xx, 5xx), redirected, `304` and cached requests all count. Each is a request the page made.
- `data:` and `blob:` URLs are already filtered out by the recording (EPIC-BP2 §8).

### Grade

These are owner decisions on the number **n** of requests. The request's overlapping bounds were resolved by the PO as below.

- **A:** n ≤ 40: "<n> requête(s) HTTP".
- **B:** 41 ≤ n ≤ 70.
- **C:** n ≥ 71.
- **Detail for B and C:** "<n> requêtes HTTP (40 au plus recommandées)".

### Offender lines

There are none. The detail is enough, because the request list is already in the page detail.

## 3. Tech Stack Hints & Scope Constraints

- **In scope:** a pure `evaluate()` on `RuleContext.requests`.
- **Out of scope:**
  - breakdown by type or domain (US-011 covers domains);
  - deduplication;
  - weighting by size.
- **State:** synchronous.
- **Persistence:** stored with the page.

## 4. Acceptance Criteria (Gherkin Scenarios)

### Scenario 1: Happy path
Given the page made 25 requests
When the best practices are evaluated
Then the rule is graded "A" with the detail "25 requêtes HTTP"

### Scenario 2: Boundary, 40 gives A and 41 gives B
Given the page made 40 requests
Then the rule is graded "A"
Given the page made 41 requests
Then the rule is graded "B" with the detail "41 requêtes HTTP (40 au plus recommandées)"

### Scenario 3: Boundary, 70 gives B and 71 gives C
Given the page made 70 requests
Then the rule is graded "B"
Given the page made 71 requests
Then the rule is graded "C"

### Scenario 4: Every request counts
Given the page made 38 successful requests, 2 requests answered 404, 1 answered 304 and 1 redirect
Then n is 42 and the rule is graded "B"

### Scenario 5: Same count as the page table
Given any recorded page
Then n equals the number shown in its "Requêtes" column

### Scenario 6: No request
Given a page with 0 recorded requests
Then the rule is graded "A" with the detail "0 requête HTTP"

## 5. Non-Functional Requirements (NFRs) & Constraints

- **Performance:** constant time.
- **Accessibility:** no new UI.
